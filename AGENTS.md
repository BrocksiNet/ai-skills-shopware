# Agent guide — ai-skills-shopware

This repository is a **curated Agent Skills library** for Shopware 6 development.
It is not a Shopware instance — there is no `vendor/`, no kernel, and no runtime
to boot. Work here means authoring skills, references, and eval tasks, then
proving they change model behavior.

Human onboarding: [`README.md`](README.md). Skill ownership and topic boundaries:
[`REGISTRY.md`](REGISTRY.md).

## Concepts at a glance

The terms the rest of this guide uses. Details follow in the sections linked.

| Term | Meaning |
| ---- | ------- |
| Rule ID | `PLG-028`: prefix of the owning skill plus a number. Written bold once where the rule is stated, as a code span everywhere else. Never reused. See [Adding or changing a rule](#adding-or-changing-a-rule). |
| Catalog | `rules/catalog.json`: one entry per rule with its file, eval task (or why there is none), `audience` and what core already enforces. |
| Audience | Who a rule is for: `core`, `plugin`, `app`, `storefront`, `admin`. The extension review reports only `plugin` and `app` rules. |
| Route | An entry in a skill's `routes.json`: which reference to read when a diff touches these paths (`paths_any`) or lines (`anchors_any`), on every change (`always`), or when the task asks for it (`on_demand`). See [Adding or changing a reference](#adding-or-changing-a-reference). |
| Skill metadata | The `metadata:` block in a `SKILL.md` frontmatter: `contexts` (core, plugin, app, project), `tasks` (build, review, ship, answer, run), optional `load_for`, `paths` and `defers_to` (the core trunk skills that lead on the topic). `sw-skill-router` filters on it. |
| Router index | `skills/sw-skill-router/index.json`: every skill's metadata and resolved routes, generated by `tools/bin/render-router-index.ts`, so the installed router needs no repo tooling. |
| Borrowed route | A route to `../<skill>/references/<file>.md`. It takes its triggers from the owning skill, so a review skill reuses rules without copying them. |
| Review pair | Two tasks per rule: `review-<rule>-catch` (a diff with the problem; the findings must name it) and `review-<rule>-ignore` (a clean diff that looks similar; no finding allowed). Graded by `reviewCatch` and `reviewIgnore` in `tools/src/grade/review.ts`. |
| Near-miss task | `review-<topic>-near-miss`: a real problem next to a rule that does not cover it. The finding must report it without citing that decoy rule. Guards against the most common review error, a plausible but wrong rule ID. |
| Golden fixtures | `fixtures/pass/` and `fixtures/fail/` of a task: known answers the grader must pass and fail on every push, so a grader cannot silently go soft. |
| Enforced by CI | A generated `SKILL.md` section listing rules an existing check (PHPStan, ECS, ESLint, Danger, a core test) already catches, so the agent does not repeat them. |
| Drift mining | The weekly `trunk-drift` issue about changes on `shopware/shopware` trunk and the upstream skill sets in `rules/sources.json`, grouped by the skill and rule each change touches; `docs/.mining-state.json` marks how far each source has been read. See [`docs/maintenance.md`](docs/maintenance.md#reading-the-drift-issue). |

## Repository layout

```text
skills/<skill-name>/
  SKILL.md                    # frontmatter + progressive-disclosure body
  references/*.md             # loaded on demand from SKILL.md links
  routes.json                 # which reference a change needs (globs + line regexes; may borrow ../<skill>/references)
  evals/should-trigger.md       # activation eval prompts (must trigger)
  evals/should-not-trigger.md   # activation eval prompts (must stay quiet)

evals/tasks/<task-name>/
  instruction.md              # prompt given to the agent
  fixture/                    # starting code (negative / pristine case)
  fixtures/pass/              # golden workdir that must PASS grade.sh
  fixtures/fail/              # optional golden FAIL case
  grade.sh                    # fixed entry: runs tools/graders/<task>.ts (or an AST grader)
  skills                      # optional: extra skills for smoke A/B (one name per line)

evals/smoke/                  # local A/B harness (Claude, Codex, Cursor CLI)
evals/runner/                 # shell wrappers for tools/bin (fake-agent.sh is the test double), install-agent.sh
evals/harbor/                 # containerized Harbor wiring (optional)
evals/test-graders.sh         # golden tests for all grade.sh scripts (wrapper for tools/bin/test-graders.ts)
evals/tools/ast/              # Node AST graders (php-parser + @babel/parser)
evals/routing/<case>/         # diff.patch + expected.json for reference routing

rules/

  bin/skills-profile.ts       # skills on/off per eval workdir

  bin/validate-skills.ts      # skill structure, budgets, conflicts, rule IDs, routes

  src/map-signal.ts           # ties a change (signal) to the skills, references and rules it touches

  src/grade/                  # grader kit (file search, comment stripping, PHP method, review findings)
  bin/test-graders.ts         # golden fixtures against every grade.sh
  bin/fake-agent.ts           # test double for SKILLS_AGENT_CMD
  bin/check-update.ts         # pinned version vs latest release tag
  test/*.test.ts              # node --test
  api-index/                  # public API index of shopware/shopware per release (own package: php-parser):
                              # bin/build.ts one ref, bin/timeline.ts all tags, bin/api-facts.ts an extension's facts,

scripts/

  evals.yml                   # model evals (gated: schedule, label, dispatch)
```

Skills install into provider-specific folders (`.cursor/skills/`, `.claude/skills/`,
`.codex/skills/`, `.agents/skills/`) via [`skills.sh`](https://github.com/vercel-labs/skills).
This repo **authors** those folders; it does not contain installed copies.

## Before you change anything

Run the deterministic checks (same as CI):

```bash
bash scripts/validate-skills.sh
bash scripts/run-activation-evals.sh
( cd tools && npm ci && npm run typecheck && npm run lint && npm run format:check && npm test )
( cd evals/tools/ast && npm ci && npm test )
bash evals/test-graders.sh
```

ShellCheck (optional locally; required in CI):

```bash
mapfile -t files < <(
 find evals/smoke evals/runner scripts evals evals/tools/ast -maxdepth 1 -name '*.sh' -type f | sort
)
shellcheck "${files[@]}"
```

Model A/B with an agent you are logged in to (no API key; costs your plan's
usage):

```bash
EVAL_TASKS=prepare-plugin-for-6-8 REPEATS=3 bash scripts/eval-local.sh
```

Smoke harness — graders only (no API cost):

```bash
./evals/smoke/smoke.sh graders
./evals/smoke/smoke.sh agents    # list agent CLI availability
```

## Eval layers

| Layer | What | Cost | CI |
| ----- | ---- | ---- | -- |
| 0 | `validate-skills.sh`, ShellCheck, golden graders, markdown lint | free | every push |
| 1 | Activation — right skill loads for trigger phrases | agent API | dry on push; real in `evals.yml` |
| 2 | Behavioral — `evals/tasks/<task>/` + `grade.sh` | agent API | via `evals.yml` when configured |
| 3 | A/B ablation — skill on vs off | agent API | `evals/runner/ab.sh` or `evals/smoke/smoke.sh suite` |

Details: [`evals/README.md`](evals/README.md). Local A/B smoke:
[`docs/smoke-evals.md`](docs/smoke-evals.md).

### Grader contract

Graders receive:

- `WORKDIR` — directory with fixture + agent edits
- `TRANSCRIPT` — path to the agent's textual output

Every task keeps a `grade.sh`, because Harbor, the smoke harness and the
runner call it. It is the same two-line wrapper everywhere: it runs
`node tools/bin/grade.ts <task>`, which loads
[`tools/graders/<task>.ts`](tools/graders/) and prints `score=1 (…)` or
`score=0 (…)`. Write the checks there, as `export const grade: Grader`, with
the helpers in [`tools/src/grade/kit.ts`](tools/src/grade/kit.ts):

```ts
export const grade: Grader = ({ workdir }) => {
  const file = findFile(workdir, 'UserValidator');
  if (file === undefined) return fail('UserValidator.php not found');
  const text = read(file);
  const usesEmpty = hasLine(text, /\bempty\s*\(/u);
  return verdict(!usesEmpty, { uses_empty: usesEmpty });
};
```

Prefer grep/AST and project tooling (PHPStan, ECS, PHPUnit via `vendor/bin/`
when present) over LLM-as-judge. For PHP/JS **structure** (attribute on a
named method, real `import`/`export`, not a comment or leftover file), add a
predicate under [`evals/tools/ast/`](evals/tools/ast/) and thin-wrap `grade.sh`
through `evals/tools/ast/run-grade.sh`. Evals-only `npm ci` there is allowed;
do not add Composer or a Shopware `vendor/`. Golden fixtures in
`fixtures/pass/` and `fixtures/fail/` are tested by `evals/test-graders.sh` on
every push. `fixture/` is also graded as FAIL unless the task has
`.skip-fixture-grade`.

Before you ship a grader, check these yourself (Copilot keeps finding
the same holes):

- Prefer the **structural relationship** that matters over “several strings
  occur somewhere”. Scope checks to the subject file, method, class, or
  template block. Use [`evals/tools/ast/`](evals/tools/ast/) for PHP/JS
  structure. `stripComments`, `phpMethod` and `jsCallArgs` in the kit scope
  a check to code, one method or one call.
- A token in a comment, leftover file, or unused call is not a pass.
- Accept common compliant rewrites (receiver variables, named-arg order,
  async `import()`, official `main.js` / `mt-popover`).
- Do not forbid an allowed API (client `fetch({ cache: 'no-store' })` is
  not a document-cache header).
- New graders need `fixtures/fail/` as an **almost-pass sneak** (what a
  token-only check would have accepted). The pristine `fixture/` start
  dir is not that sneak.

Review-shaped tasks (`review-<rule>-catch` / `-ignore`) grade the findings
JSON in `TRANSCRIPT`: their grader is one call to `reviewCatch`,
`reviewIgnore` or `reviewNearMiss` from `tools/src/grade/review.ts`. Layout and
contract: [`evals/README.md`](evals/README.md#review-tasks-review-rule-catch---ignore).

## Adding or changing a rule

1. Confirm the [five inclusion criteria](README.md#curation--governance) in README.
2. Assign the topic to **exactly one** skill in [`REGISTRY.md`](REGISTRY.md)
   coverage matrix — never duplicate ownership.
3. Write the rule in the owning `SKILL.md` (or `references/*.md` if long).
   Link references from `SKILL.md`; `validate-skills.sh` checks dead links.
4. Give it the next free ID for the skill's prefix (see `prefixes` in
   [`rules/catalog.json`](rules/catalog.json)) and start the rule's bullet with
   the bold ID: `- **TEST-035** Never …`. Tag the bullet that states the rule
   once. A `SKILL.md` summary of a rule tagged in a reference stays untagged;
   point at another rule with a code span, `` `PLG-011` ``.
5. Add the catalog entry: `file`, `title`, `eval` (task name) or `eval: null`
   with an `eval_reason`, and `trunk` / `defer_on_trunk` when core has the
   rule. When the rule comes from a trunk guideline or an upstream skill
   set, set `trunk.source` or `upstream` to `path#heading-anchor`, so the
   weekly drift issue files later changes there under this rule. Never reuse an ID; a dropped rule becomes `retired` or
   `superseded:<ID>` and leaves the skill text.
   When a CI check already catches the rule, add it to `trunk.enforced_by`
   (`tool`, `kind`, `catches`, `misses`, `trunk_only`) from the check's source,
   then run `node tools/bin/render-enforced.ts`. It writes the skill's
   `## Already enforced by CI (do not repeat)` section; never edit that
   block by hand.
6. Add activation prompts under `skills/<skill>/evals/`.
7. Add a behavioral task under `evals/tasks/<rule>/` with the `grade.sh`
   wrapper, its grader in `tools/graders/<task>.ts`, and golden fixtures (`fixtures/pass/` required when the rule is gradable). For PHP/JS
   structure, add `evals/tools/ast/src/tasks/<rule>.mjs` and thin-wrap `grade.sh`.
   Then set the rule's `eval` to the task.
8. Re-run `validate-skills.sh` (it runs `tools/bin/validate-rules.ts`), `evals/tools/ast`
   snippet tests, and `evals/test-graders.sh`.

Tagged so far: `sw-testing`, `sw-plugin-development`,
`sw-review-learnings`, `sw-core-development`, `sw-admin-js`,
`sw-architecture`, `sw-storefront`, `sw-security`,
`sw-change-impact`. Tag a skill's remaining rules when you next touch it.

For recurring real-world findings, prefer `sw-review-learnings` and point
at the owning skill rather than re-defining the topic.

## Adding a skill

1. Create `skills/sw-<name>/` with `SKILL.md` (`name` must match folder).
   Every skill name starts with `sw-`.
2. Keep `description` under 1024 chars and `SKILL.md` under 500 lines.
   Add the `metadata:` block (`contexts`, `tasks`, and `load_for` or
   `paths` when the skill should load with no reference matching), then
   run `node tools/bin/render-router-index.ts`. Mention the skill in
   `skills/sw-help/SKILL.md`; `validate-skills.sh` fails otherwise.
3. Add `evals/should-trigger.md` and `evals/should-not-trigger.md`.
4. Register the skill and its topics in [`REGISTRY.md`](REGISTRY.md).
5. Add install lines to README / relevant `use-cases/*.md` if it is a new
   use-case surface skill.

## Adding or changing a reference

Every `references/*.md` file needs a route in the skill's `routes.json`:
`reference`, `when` (the task in words), and `paths_any` globs and/or
`anchors_any` regexes on added and removed diff lines. Two kinds of route
have no triggers: `always: true` when every change the skill sees needs the
reference, and `on_demand: true` when the task decides and nothing in a diff
says so (an approach keeps failing, a fix grows beyond the bug). Keep
triggers specific; a route that fires on any PHP file defeats the point, and
a proxy trigger is worse than `on_demand`.

`exclude_paths` lists globs of changed files a route ignores, for paths and
anchors alike, so a production-code rule does not fire on a test, an ADR or
release notes. A top-level `exclude_paths` in `routes.json` is the default
for every route without its own list; `"exclude_paths": []` opts a route
out. A borrowed route takes the lender's exclusions. Then:

```bash
node tools/bin/render-routes.ts        # rewrites the table between the routes markers
git diff main | node tools/bin/route.ts  # selected by the diff, plus always and on_demand
node tools/bin/render-router-index.ts  # the router index ships the routes too
```

When a change alters what a case in `evals/routing/` should select, update
its `expected.json`; add a case for a new kind of change. `expected.json`
lists only diff-selected references, never `always` or `on_demand` ones.

A route can borrow another skill's reference: `"reference":
"../<skill>/references/<file>.md"` with no triggers of its own takes `when`
and the triggers from the owning skill's route, so the two cannot drift.
`sw-extension-review` reads the topic skills this way. Its
`routes.json` sets `audience`; a rule in a borrowed reference that is for
none of those audiences must be named in the skill (`references/lenses.md`),
or `validate-rules` fails. The other way round, a rule a review task expects
(a `-catch` grader's `rule`, a near-miss grader's `accept`) must be tagged in
a reference the review borrows, not in a topic skill's `SKILL.md`: the
review never reads that, and cites the nearest ID it did read instead.

## Repo tooling

New tooling is TypeScript in [`tools/`](tools/): Node 24 runs the `.ts` files
directly (type stripping, so only erasable syntax: no `enum`, no parameter
properties, no namespaces). `npm run typecheck` runs `tsc` with `strict`;
`npm test` runs `node --test`. Keep runtime dependencies at zero where you
can, so `node tools/bin/<tool>.ts` works without `npm ci`. The eval runner
and the task graders live here; what is left in shell are thin wrappers
that keep old entry points working. The AST graders in `evals/tools/ast/`
stay JavaScript, because they need `php-parser` and `@babel/parser`.
`tools/api-index/` is TypeScript with its own `package.json`, because the
index generator needs `php-parser`; `npm ci --prefix api-index` before the
type check. The tools that read the index stay dependency-free.

`npm run lint` runs oxlint with type-aware rules
([`tools/.oxlintrc.json`](tools/.oxlintrc.json)), and `npm run format`
formats with oxfmt. CI fails on any finding or formatting drift, so fix the
code rather than adding a disable comment. In practice:

- Parse JSON to `unknown` and narrow it with a type guard; no `as` casts and
  no `!` assertions.
- Read settings with `envOr` and `envInt` from `src/env.ts`, never with
  `env.X || default`. Turn caught values into text with `errorMessage` from
  `src/errors.ts`.
- A bin sets `process.exitCode` from a `main()` and returns. Run agent work
  one after another with `inSeries` from `src/series.ts`.

## What not to do here

- Do not run host `php`, `composer`, or `phpunit` against a Shopware tree from
  this repo — there is none. Test graders use fixture workdirs only. The
  Node install under `evals/tools/ast/` is evals-only, not a Shopware runtime.
- Do not add rules without an eval — untested guidance belongs in docs, not skills.
- Do not copy upstream skills verbatim — rewrite in our words; see README credits
  and license notes in REGISTRY.
